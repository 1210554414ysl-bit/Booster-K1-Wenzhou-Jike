# 05 · 版本管理：别让一个坏 Agent 毁掉机器人

> **目标**：任何一次改动都能退回上一个「确认能用」的状态；任何时候装到机器人上的，都是你亲手验证过的包。

---

## 0. 先说结论：机器人会不会被搞死？

**大概率不会。** 先分清两件事：

| 东西 | 是什么 | 装坏了会怎样 |
| --- | --- | --- |
| **Agent** | 机器人系统上的一个「应用」，像手机 App | 删掉 / 切回官方 Agent 就恢复了 |
| **机器人系统** | 固件、语音、运动控制、App 连接 | 我们改不到它 |

所以「Agent 有 bug」通常的表现是：**打开这个 Agent 没反应 / 报错 / 界面卡住**。
你现在就能救：App → 左上角 Agent 名称 → **长按该 Agent → 删除** → 切回「Booster」官方 Agent。

**唯一需要警惕的情况**：Agent 在**主线程回调里做耗时操作**，把 App 界面卡死，连删除按钮都点不动。那时才需要：
- 重启机器人，或
- SSH 上去把 Agent 目录删掉

这正是 `docs/03-develop-agent.md` 里反复强调「回调必须快速返回」的原因。

> ✅ 所以策略是：**用 git 保住「能用的版本」，用流程保证「装上去的是验证过的版本」**。

---

## 1. 四个 git 概念，用大白话

| 概念 | 大白话 | 在你这个场景里 |
| --- | --- | --- |
| **仓库 (repo)** | 一个带历史记录的项目文件夹 | 就是现在这个 `Booster-K1-Wenzhou-Jike` |
| **提交 (commit)** | 一次「存档 + 备注」 | 每次改完代码存一档，写清改了什么 |
| **标签 (tag)** | 给某个存档点起个永久名字 | 每个**能装上机器人正常跑**的版本打一个 `music-player-v1.0.0` |
| **分支 (branch)** | 平行世界，改坏了不影响主线 | `main` = 永远能用；`dev` = 正在改的 |

**最重要的一句**：git 管的是**代码**，`.agent` 安装包是构建产物。要能「退回上一版」，你必须把**能用的 `.agent` 也存下来**（本仓库的做法：每个 Agent 目录里直接放一个 `.agent`，随代码一起提交）。

---

## 2. 三条铁律

### 铁律一：`main` 分支永远是「能用的」
`main` 上的任何一次提交，都应该是**你验证过、可以装到机器人上**的状态。
想乱改？开 `dev` 分支去改，改成功了再合并回来。

### 铁律二：每个能用的版本，都打 tag
打完 tag，你永远能一条命令回到那个状态：
```bash
git checkout music-player-v1.0.0     # 回到这个版本
```
忘了打 tag = 找不回来。

### 铁律三：装机器人之前，先提交
**安装前**：确认代码已提交、`.agent` 已是最新构建。
**安装后**：立刻在这里打 tag，或记进 `CHANGELOG.md`。
这样"机器人上跑的那个版本"永远能对上仓库里的某个 commit。

## 3. 日常开发流程（照着做就行）

```
① 拉最新          git pull
② 开分支改        git checkout -b dev
③ 改代码
④ 提交            git add -A && git commit -m "feat: 加了什么"
⑤ 构建 + 测试     Booster Studio 里构建；本地跑冒烟测试
⑥ 装真机验证      ⭐ 这一步没过，不许合并
⑦ 合并回 main     git checkout main && git merge dev
⑧ 打 tag          git tag -a music-player-v1.1.0 -m "新增xx功能"
⑨ 推送            git push origin main --tags
```

**新手最容易漏的是第 ⑥ 步**。git 不会帮你验证，它只负责保存。**"能不能用"永远靠你装到机器上点一遍。**

---

## 4. 出问题了怎么回滚（两种场景）

### 场景 A：机器人上装的新版本有问题，想退回旧版本

**不需要碰 git**，直接用旧包覆盖：

1. App → Agent 列表 → **长按该 Agent → 删除**（先清掉坏的）
2. 从 GitHub **Releases** 页面下载上一个版本的 `.agent`
3. 在 Booster Studio 里安装这个旧包
4. 验证功能正常

> 为什么要先删？同名包覆盖安装会走「升级」流程；**降级（版本号变小）建议先删后装**，最保险。

### 场景 B：代码改坏了，想回到某个能用的版本

```bash
git log --oneline                 # 看历史，找到目标 commit
git checkout music-player-v1.0.0  # 直接回到那个 tag（只读查看）
# 或者：把那个版本恢复成一个新分支继续改
git checkout -b fix-from-v1.0.0 music-player-v1.0.0
```

> ⚠️ 注意：`git checkout <tag>` 只是"去看"，不要在上面直接改。要改就开新分支。

## 5. 版本号怎么定（语义化版本）

格式：`主版本.次版本.修订号`，例如 `1.2.3`

| 什么时候升 | 升哪一位 | 例子 |
| --- | --- | --- |
| 修 bug，功能不变 | 修订号 | `1.0.0` → `1.0.1` |
| 加新功能，旧功能不变 | 次版本 | `1.0.1` → `1.1.0` |
| 改了界面/配置，旧用法不兼容 | 主版本 | `1.1.0` → `2.0.0` |

**升版本号必须改 `agent.toml` 里的 `version`**，因为它决定 `.agent` 包名：
```
com.wenzhoujike.k1.music-1.0.0.agent
                          ↑
                       改这里
```

不升版本号直接覆盖安装 → 机器人可能认为「版本没变」，不触发升级，你看到的行为还是旧的。**这是最常见的"改了没用"原因。**

## 6. 分支策略（够用版，别搞复杂）

只要两个分支：

```
main    ●────────●────────────●──────────────●   （能用的版本，打 tag）
         \       /  \         /
dev       ●──●──●    ●──●──●─●                   （日常开发）
```

- `main`：只接受验证过的合并
- `dev`：随便改。改崩了删掉重建也不心疼

**不要**一开始就搞 `feature/*`、`release/*`、`hotfix/*`，新手会被自己绕晕。

## 7. 每次发布要做的事（本仓库有一条命令）

```powershell
# 在仓库根目录
.\\scripts\\release.ps1 -Agent music-player
```

它会自动：
1. 读 `agent.toml` 里的 id 和 version
2. 把 `build/` 里刚构建的 `.agent` 归档到 `agents/music-player/`（随 git 提交）
3. 校验工作区是否干净
4. 提交并打 tag `music-player-v1.0.0`
5. 提示你推送

加 `-Push` 参数会顺便推 tag 并创建 GitHub Release（可下载的安装包）。

## 8. 命令速查表（背这几个就够）

| 想干什么 | 命令 |
| --- | --- |
| 看现在改了哪些文件 | `git status` |
| 看历史提交 | `git log --oneline` |
| 把改动全部存档 | `git add -A && git commit -m "说明"` |
| 拉最新代码 | `git pull` |
| 推送到 GitHub | `git push` |
| 推送标签 | `git push --tags` |
| 开分支 | `git checkout -b dev` |
| 切分支 | `git checkout main` |
| 看所有标签 | `git tag` |
| 回到某个版本 | `git checkout <tag>` |
| 查看某次提交改了什么 | `git show <commit>` |
| 撤销还没提交的改动（⚠️会丢） | `git checkout -- .` |

## 9. 这个仓库的具体约定

```
Booster-K1-Wenzhou-Jike/
├── agents/
│   └── music-player/
│       ├── agent.toml                        ← version 字段 = 版本号
│       ├── src/main.py                       ← 源码
│       └── com.wenzhoujike.k1.music-1.0.0.agent  ← ⭐ 能用的安装包（一起提交）
├── CHANGELOG.md                              ← 版本变更记录
├── docs/
└── scripts/
    └── release.ps1                           ← 一键发布
```

- **tag 命名**：`<agent名>-v<版本号>`，例如 `music-player-v1.0.0`、`volume-adjustment-v1.0.0`
- **提交信息**：`feat:` 新功能 / `fix:` 修 bug / `docs:` 文档 / `chore:` 杂项
- **`.agent` 是二进制**，git 存得下但看不见 diff，所以每次发布都要打 tag 并在 `CHANGELOG.md` 里写一行

---

## 10. 最后：给「怕装坏」的人一条保险绳

**每次往机器人上装之前，做这三件事：**

1. ✅ 确认上一个能用的 `.agent` 在仓库里（`git log` 能看到）
2. ✅ 确认 App 里还能进 Agent 列表（能长按删除）
3. ✅ 记下当前机器人的 Agent 版本号

**装完发现不对，30 秒内能恢复：** 删掉新装的 → 装回上一个能用的包。
