# 05 · 版本管理、发布与回退

Git 保存源码历史，`.agent` 保存实际安装内容。两者需能对应到同一版本；tag 只是版本定位点，不代表自动通过测试，也不代表已创建 GitHub Release。

## 当前发布与历史

当前推荐包和验证范围见 [首页](../README.md) 和各 Agent README。仓库目录中保留安装包；部分历史版本还在 [Releases](https://github.com/1210554414ysl-bit/Booster-K1-Wenzhou-Jike/releases) 有附件。没有 Release 的版本可以从对应 tag 的 Agent 目录取包。

历史版本见 [CHANGELOG](../CHANGELOG.md)。本地播放器早期版本曾有平台接入能力，当前 1.2.1 的功能以其 README 为准。不要把旧版本变更当作当前功能介绍。

## 开发与发布流程

1. 从当前主线开工作分支，记录需求和验收条件。
2. 修改并审查明确范围的文件；检查暂存区，避免带入凭据或不相关产物。
3. 按 Agent 自己的构建说明生成签名安装包，核对版本、资源与运行依赖。
4. 执行关键流程回归，分别记录模拟、真机安装、音频输出与手机操作的结果。
5. 未完成的验证明确列出；通过相应验收后再设为推荐版本。
6. 提交源码、包和文档，创建 `<目录名>-v<版本>` tag，推送明确的提交和标签。
7. 从 GitHub 下载公开文件，核对 SHA-256 和安装步骤。按需创建 Release 并上传附件。

每次交付列出“已验证、未验证、已知限制”。`main` 不自动等于所有机型可用；具体兼容范围由包声明与测试记录共同说明。

## 版本号与签名

功能修改通常递增次版本，兼容性修复递增修订号；破坏兼容时再考虑主版本。保持 `agent.toml`、运行清单、包内版本与文件名一致。

同 ID 的更新沿用原签名证书。版本号变化本身不能证明包内容已更新，升级后需读取安装信息并实际验证。

## 已有发布脚本的适用范围

`scripts/release.ps1` 是已有的发布辅助脚本，本次文档审查未修改它。使用前阅读脚本：

- 要求目录内有 `agent.toml`，从 `build/` 选择最新 `.agent` 并核对文件名。
- 会执行 `git add -A`，将工作区所有变更暂存后提交；不会只提交指定 Agent，也不会替你检查或排除私密文件。
- 可创建 tag，`-Push` 推送 `main` 与关联标签；仅在 `gh` 可用且调用成功时创建 Release。
- 不负责运行测试、验证签名、检查资源完整性或完成真机验收。
- 在线音乐使用自定义打包流程，不能直接假定适用；音量调节目录未提供完整 TOML 工程。

不要把脚本执行完成当作质量验收完成。尚未熟悉其行为时，优先按上面的步骤手动审查和发布。

## 故障回退

先切换到可用的 Agent，保留错误日志和当前版本信息。备份私有存储中的歌曲、配置和账号数据后，再评估降级或卸载；系统可能限制低版本或不同证书覆盖安装。

使用已保存且经过验证的历史签名包，按 [安装说明](02-install-agent.md) 安装并验证。不要手动删除机器人系统目录来代替管理器卸载；不承诺固定时间内恢复，也不能保证卸载后数据仍保留。

只查看历史源码可以使用：

```bash
git log --oneline
git show music-player-v1.2.1
git switch -c inspect-music-1.2.1 music-player-v1.2.1
```

Agent 可以调用音频及其他机器人接口，错误实现可能影响系统资源或设备行为，因此测试与备份都不能省略。
